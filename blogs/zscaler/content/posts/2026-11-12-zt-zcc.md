これまでの記事で、ZIA・ZPA・ZDX をそれぞれ取り上げてきました。そのすべてに共通する入口が、利用者の端末に入れるエージェント **Zscaler Client Connector**（ZCC）です。
今週の製品別アップデートでも、ZCC の修正に「Z-Tunnel 2.0」「Transparent Proxy-based Interception」といった言葉がたびたび出てきました。
この記事では、ZCC の役割と、通信の送り方を決める**転送プロファイル**、そして **Z-Tunnel 1.0 と 2.0 の違い**を、公式ドキュメントで確認できた範囲で整理します。

## Client Connector の役割

公式ドキュメント「What Is Zscaler Client Connector?」では、ZCC を次のように説明しています。

- 端末にインストールする、軽量で改ざんに強いソフトウェア
- 利用者と端末の通信を、Zscaler の Zero Trust Exchange に自動的に転送する
- 利用者がどこにいても、インターネットと社内アプリの両方に、検査とポリシーを効かせる

設定は管理画面（Zscaler Admin Console）で行い、Windows と macOS には利用者に意識させずに配布（サイレントインストール）できます。Android・ChromeOS・iOS には MDM（モバイル端末管理）で配布します。
利用者がログインして端末を登録すると、管理画面で設定した内容と、その利用者に割り当てられた **アプリプロファイル** が端末に届きます。

## 転送プロファイル：場所によって通信の扱いを変える

**転送プロファイル**（Forwarding Profile）は、端末がどんなネットワークにいるかに応じて、ZIA と ZPA の通信をどう扱うかを決める設定です。
ZCC は、次のネットワーク環境を見分けます。

| 環境 | 意味 |
|---|---|
| On-Trusted Network | 社内の信頼済みネットワークにいる。判定条件（Trusted Network Criteria）の設定が必要 |
| VPN-Trusted Network | VPN のフルトンネルで社内につながっている。VPN が既定経路（デフォルトルート）を入れている必要がある |
| Split VPN-Trusted Network | VPN のスプリットトンネル（一部の通信だけ VPN）で社内につながっている |
| Off-Trusted Network | 上のどれでもない、信頼できないネットワーク（自宅・カフェなど） |

たとえば「社内にいるときは拠点のトンネルで ZIA に送るので ZCC は何もしない」「社外では ZCC がトンネルで送る」といった使い分けを、この転送プロファイルで決めます。
転送プロファイルは何個でも作れて、アプリプロファイルで利用者ごとに割り当てます。

### VPN と併用するときの落とし穴

公式ドキュメントによると、次のような場合、VPN につないでいても ZCC は **Off-Trusted Network** と判定します。

- VPN が既定経路を入れず、別の方法で全通信を取り込んでいる
- Windows で、既定のインターフェースの説明に Cisco・Juniper・Fortinet・PanGP・VPN のいずれの語も含まれない（macOS は代わりに、VPN が utun・PPP・GPD のインターフェースを作ったかで判断する）
- VPN がスプリットトンネルで、一部の通信だけを取り込んでいる

既存の VPN と ZCC を併用する移行期間は、「社内扱いのはずが社外扱いになっていた」というずれが起きやすいところです。端末の ZCC の画面に表示されるネットワーク種別で、判定結果を確認しましょう。

| | Z-Tunnel 1.0 | Z-Tunnel 2.0 |
|---|---|---|
| 仕組み | CONNECT 要求で転送する、従来のプロキシに近い方式 | DTLS または TLS でパケットを送るトンネル方式 |
| 送れる通信 | プロキシに対応した通信、または 80/443 番ポートの通信（設定による） | 全ポート・全プロトコル |
| 必要な設定 | 転送プロファイルで Z-Tunnel 1.0 を選ぶ | 対応バージョンの ZCC を配布し、Z-Tunnel 2.0 を選び、アプリプロファイルで迂回（バイパス）を設定する |

Z-Tunnel 2.0 なら、Web 以外のアプリの通信も ZIA に送って、ファイアウォールなどの機能で検査できます。今週の ZCC の修正に、DNS の通信や DTLS が遮断されたネットワークに関するものが多かったのは、Z-Tunnel 2.0 が Web 以外の通信まで扱うためです。

### Z-Tunnel 2.0 の注意点

- **NAT 機器**：1台の端末からの接続を、すべて同じ1つの IP アドレスで送る NAT を使う必要があります。そうでないと、制御用とデータ用の接続が別々の Service Edge に届いてしまい、Z-Tunnel 2.0 が確立できずに **Z-Tunnel 1.0 に戻ります**
- **バイパスの設計**：全通信を送るぶん、Zscaler に送るべきでない通信（社内のネットワーク範囲など）をアプリプロファイルで除外する設計が欠かせません

## 導入の進め方（公式のベストプラクティス）

公式ドキュメント「Best Practices for Deploying Z-Tunnel 2.0」は、Z-Tunnel 2.0 の展開を5つの段階で進めることを勧めています。

1. 対象ユーザーのグループを決め、Z-Tunnel 2.0 の設定をする
2. ICMP の通信をブロックして、初期テストをする
3. 社内ネットワークの範囲を Z-Tunnel 2.0 から除外する
4. 同じグループで1〜2週間テストを続ける
5. 対応バージョンの ZCC と Z-Tunnel 2.0 を全ユーザーに展開する

いきなり全社に切り替えず、小さなグループで社内システムへの影響を確かめてから広げる流れです。公式ドキュメントも、全ユーザーへの展開時の設定は、テスト時の推奨設定と違ってよいとしています。

## よくある落とし穴

- **Z-Tunnel 2.0 のつもりが 1.0 で動いている**：NAT の構成によっては 1.0 に戻ります。端末で実際に使われているトンネルの種類を確認しましょう
- **社内扱い・社外扱いの判定ずれ**：信頼済みネットワークの判定条件や、VPN との併用条件を確認します
- **バイパスの設計漏れ**：社内向けの通信まで Zscaler に送ってしまい、社内システムにつながらなくなる例があります。段階的な展開で早めに見つけます

## まとめ

- Client Connector は、ZIA・ZPA・ZDX・Endpoint DLP の共通の入口になる端末エージェント
- 転送プロファイルで、社内・VPN・社外といったネットワーク環境ごとに通信の扱いを決める
- Z-Tunnel 1.0 はプロキシ型、2.0 は DTLS/TLS のトンネル型で全ポート・全プロトコルを送れる。2.0 は NAT の条件とバイパス設計に注意

設定の具体的な手順や最新の仕様は、必ず [Zscaler Help](https://help.zscaler.com/zscaler-client-connector) の公式ドキュメントで確認してください。
