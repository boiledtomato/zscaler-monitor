Zscaler の製品別アップデート、今週の1本目は端末側のエージェント **Zscaler Client Connector（ZCC）** です。
10月30日〜11月5日に、Windows・macOS・Linux 向けに合計11のバージョンが公開されました。
すべてのバージョンに共通するのは、**漏えいした eMudhra の中間証明書を信頼しない**というセキュリティ上の変更です。あわせて、macOS では **IPv6 の扱いが変わる**変更が入っています。どの設定の人に関係するのかを、図を使って整理します。

## 全OS共通：eMudhra の中間証明書を信頼しない

**何が変わったか**
すべての新バージョンで、証明書の発行事業者 eMudhra に関連する、漏えいした TLS 中間証明書を除外するようになりました。Client Connector がルート証明書を読み込むときに、これらの証明書を信頼の対象から外します。

**どんな機能か（背景）**
HTTPS では、サーバーが提示する証明書を「ルート証明書 → 中間証明書 → サーバー証明書」の鎖（チェーン）でたどり、信頼できるかを確かめます。
もし中間証明書が悪用できる状態で漏れると、攻撃者がその中間証明書で**本物そっくりの偽サーバー証明書**を作れてしまいます。こうして通信の間に割り込む攻撃を、中間者攻撃（Man-in-the-Middle、MITM）と呼びます。

Zscaler の Trust 情報（10/22 公開）によると、Zscaler の環境で侵害の証拠は見つかっておらず、Zscaler 自身も eMudhra の証明書やサービスに依存していません。そのうえで、念のため各製品の証明書リストから該当する中間証明書を取り除いています。
同じ Trust 情報では、ZPA の App Connector や Private Service Edge など**利用者が設置するコンポーネント**にも、同じ対応をした更新（26.58.5）が出ています。

**対象となる人・設定**
Client Connector を使うすべての利用者です。OS や転送方式に関係ありません。

**運用者がやること**
- 自社で配布しているバージョン系列の最新版へ、計画的に更新する
- ZPA を使っている場合は、App Connector などの自動更新の時間帯に 26.58.5 が適用されるかも確認する
- 自社のサーバーで eMudhra の中間 CA から発行された証明書を使っている場合、ZPA 経由で信頼されなくなる可能性があると Trust 情報に書かれています。該当しないかを確認しておきます

## macOS：IPv6 の扱いの変更と、セキュリティ上の修正

### IPv6 を常に許可する仕様に変更（挙動変更）

**何が変わったか**
**Transparent Proxy-based Interception モード**の macOS 端末では、IPv4 と IPv6 の両方が使えるネットワーク（デュアルスタック）で、IPv6 を常に許可するようになりました。転送プロファイルの「**Drop IPv6 in Dual Stack Network**」の設定にかかわらず適用されます。目的は、端末の CPU 使用率が高くなる問題を防ぐことです。

**どんな機能か**
Transparent Proxy-based Interception は、macOS の通信を Client Connector が取り込む方式の一つです。「Drop IPv6 in Dual Stack Network」は、デュアルスタック環境で IPv6 を落とし、通信を IPv4 にそろえるための設定です。

**対象となる人・設定**
macOS 端末で Transparent Proxy-based Interception モードを使い、転送プロファイルで Drop IPv6 in Dual Stack Network を有効にしている組織です。

**運用者がやること**
IPv6 を落とすことを前提にした設計（例：IPv4 だけを想定したポリシーやログの確認手順）があれば、IPv6 の通信が出るようになる前提で見直します。

**何が変わったか**
Strict Enforcement が有効な macOS 端末で、Transparent Proxy-based Interception モードの Client Connector にログインした直後、**トンネルを確立している間にインターネット通信が許可されてしまう**問題が修正されました。

**どんな機能か**
Strict Enforcement は、利用者が Client Connector にログインするまでインターネットへの通信を止め、「Zscaler を通らない通信」をなくすための設定です。今回の問題は、その前提に小さなすき間があったことになります。

**対象となる人・設定**
macOS 端末で Strict Enforcement と Transparent Proxy-based Interception を組み合わせている組織です。

**運用者がやること**
Strict Enforcement を「通信を必ず検査させる」ための統制として使っている場合は、優先して更新します。

### そのほかの macOS の修正

| 修正内容 | 関係する人・設定 |
|---|---|
| VPN（for Legacy Apps）が「接続中」のまま止まり、再起動まで Private Access のアプリが使えない | ZPA の VPN（Legacy Apps 向け）を使う組織 |
| FIPS モードで、公衆 Wi-Fi のキャプティブポータルにつながらない | FIPS モードを有効にしている組織（4.5.2.386 を除く） |
| Private Access 経由の社内ドメインで、Kerberos による SSO が DNS の問題で失敗する | ZPA で Kerberos 認証のアプリを使う組織 |
| 突然ログアウトされ「Service has been administratively disabled」と表示される | すべての利用者 |
| スリープ復帰後、Private Access の再認証の事前通知が届かない | ZPA の再認証を設定している組織（4.5.2.386 を除く） |
| Route-based Interception モードで Private Access を切っても経路が残る | Route-based Interception モードの組織 |
| macOS 27 で、トンネル利用中に Siri の AI 機能が断続的に失敗する | macOS 27 の利用者 |

限定提供の 5.0.0.963 では、これらに加えて、標準的でない応答を返すキャプティブポータルを検知できない問題と、UDP の 443 番が遮断されたネットワークで接続に 32〜35 秒余計にかかる問題も修正されています。

## Windows：Machine Tunnel・Business Continuity・DNS の修正

### 不正な形式の DNS で Z-Tunnel 2.0 が迂回される問題（4.9.0.508 など）

4.9.0.508 などでは、**DNS の要求が不正な形式（DNS ヘッダーが正しくないなど）だった場合に、Z-Tunnel 2.0 の通信が迂回されてしまう**問題が修正されました。DNS の対象ドメインにワイルドカード（*）を指定し、DNS サーバーを IP の対象範囲に含めていても起きていた問題です。
Z-Tunnel 2.0 で DNS をトンネルに通す設計にしている組織は、検査漏れにつながる修正なので優先して確認します。

### 主な修正

| 修正内容 | 関係する人・設定 | 対象バージョン |
|---|---|---|
| Machine Tunnel の登録時に、レジストリの情報が欠けていると ZSATrayManager が異常終了する | Machine Tunnel（ログオン前の ZPA 接続）を使う組織 | 全バージョン |
| Machine Tunnel 稼働中、Windows の PIN リセットが初回に失敗する | Machine Tunnel ＋ Windows の PIN（Windows Hello）を使う組織 | 全バージョン |
| Business Continuity 用のインストールパラメーターで入れると、ログイン時に Internal Error になる | Business Continuity を使う組織 | 4.8 以降 |
| Business Continuity モードの切り替え後、「Update App」「Update Policy」が消える | 同上 | 4.8〜4.10 |
| VMware のブリッジ接続の仮想マシンで通信が遅くなる | Windows 上で VMware を使う開発者など | 4.8・4.9・4.10 |
| スリープ復帰時のヘルスチェックの競合で、アプリが応答しなくなる | Z-Tunnel 2.0 の利用者 | 4.8 以降 |
| 断片化されたパケットを再構成できず、Private Access のアプリとの通信が止まる | ZPA の利用者 | 4.9 以降 |
| DTLS（または UDP 443）を遮断するネットワークで、接続に1〜2分余計にかかる | ホテルや社外ネットワークから使う利用者 | 4.9 以降 |
| キャプティブポータルの検知・認証の失敗 | 公衆 Wi-Fi を使う利用者 | 4.8 以降 |
| 回避（バイパス）した通信のフローログが記録されなくなる | フローログを分析している組織 | 4.7・4.8 |

あわせて、改ざん防止（Anti-Tampering）に使う ZEP（Zscaler Endpoint Protection）モジュールが 26.08.1.10 に更新されています。改ざん防止を有効にしている組織が対象です。
このほか、カスタムテーマの通知ロゴ、Endpoint AI Security 用のデバイス ID、アプリのフェイルオーバー設定（Fallback to ZIA DR）の状態表示に関する修正も含まれます。4.10.0.496 には、ここに挙げた以外の修正もあるため、詳細は公式のリリース概要を確認してください。

## Linux：ポスチャ判定と DNS の修正（4.2.2.154）

| 修正内容 | 関係する人・設定 |
|---|---|
| ZFS のネイティブ暗号化を使う Ubuntu 22.04.5 で、ディスク暗号化のポスチャ判定が誤って失敗する | ディスク暗号化のポスチャを使う組織 |
| トレイの再起動後、Microsoft Defender の検知のポスチャ結果が正しくない | Defender のポスチャを使う組織 |
| CrowdStrike のプロセス確認のポスチャが失敗する | CrowdStrike のポスチャを使う組織 |
| Z-Tunnel 2.0 の ZIA のみのモードで、DNS 通信が Zscaler に転送されない | Linux で ZIA だけを使う組織 |
| 4.2.1.114 で IPv6 を有効にすると、Ubuntu 24.04.5 LTS でトンネルが張れない | Ubuntu 24.04.5 の IPv6 環境 |

ポスチャ（端末の状態チェック）の誤判定は、ZPA のアクセス可否に直結します。Linux 端末に条件付きアクセスを設定している組織は、更新後に判定が期待どおりかを確認しましょう。

## まとめ

- 今週の ZCC は、**全OSで eMudhra の中間証明書を除外**する更新。中間者攻撃への備えとして、各系列の最新版への更新を計画する
- macOS は、Transparent Proxy-based Interception モードで **IPv6 を常に許可する挙動変更**と、**Strict Enforcement の通信漏れの修正**に注意
- Windows は Machine Tunnel・Business Continuity・Z-Tunnel 2.0 の DNS、Linux はポスチャ判定の修正が中心

次回は ZIA の週次アップデートです。各バージョンの変更の全文は、公式の [Client Connector App Release Summary (2026)](https://help.zscaler.com/zscaler-client-connector/client-connector-app-release-summary-2026) で確認してください。
