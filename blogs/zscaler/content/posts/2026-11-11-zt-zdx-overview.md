これまでの記事で、インターネット向けの ZIA と、社内アプリ向けの ZPA を取り上げてきました。
ゼロトラストの仕組みを入れると、ヘルプデスクには「前より遅くなった」「Teams の音声が途切れる」といった声が届くことがあります。原因は端末か、Wi-Fi か、自宅の回線か、Zscaler か、アプリそのものか。それを切り分けるのが **ZDX（Zscaler Digital Experience）** です。
この記事では、ZDX が「ユーザーの体感」をどう数値にしているのかを、公式ドキュメントで確認できた範囲で整理します。

## ZDX は何を測るのか

ZDX は、利用者の端末に入っている **Zscaler Client Connector** から、アプリに向けて定期的に測定用の通信（**プローブ**）を送ります。
その結果から、端末からアプリまでの各区間の状態と、利用者が感じている体感品質を数値にします。

ZIA や ZPA が「通信を守る・つなぐ」仕組みだとすると、ZDX は「その通信が快適かどうかを見張る」仕組みです。

## ZDX スコア：体感を 0〜100 で表す

ZDX の中心にあるのが **ZDX スコア**です。公式ドキュメント「Understanding the ZDX Score」によると、次のように決まります。

| カテゴリ | スコア | 色 |
|---|---|---|
| Good | 66〜100 | 緑 |
| Okay | 34〜65 | 黄（アンバー） |
| Poor | 0〜33 | 赤 |

### スコアの計算方法

- Client Connector から各アプリへ、**5分ごと**にプローブが送られる
- 5分ごとの測定結果に、0〜100 の値が付けられる
- **1時間のうち最も低い値**が、その時間の値になる
- これを、管理画面で定義したすべてのアプリについて、全ユーザー・全端末・全拠点で行う
- その結果から、アプリ別、部署・拠点・都市別、組織全体、ユーザー別のスコアが計算される

「平均」ではなく「最低値」を採るのがポイントです。1時間のうち5分だけ大きく悪化した場合でも、スコアにははっきり表れます。利用者が「さっき一瞬固まった」と感じた体験を、取りこぼさないための設計といえます。

### スコアが低くなる主な原因

公式ドキュメントでは、スコアが低い原因として次のような例が挙げられています。

- 端末の問題（再起動、CPU 使用率の高さなど）
- 接続の問題（Wi-Fi の電波の強さなど）
- アプリ自体の遅さ
- ネットワークの遅延（Wi-Fi、自宅のネットワーク、ISP など）

スコアが低い利用者がいる場合は、**診断（Diagnostics）セッション**を開始して、詳しく調べられます。

## 2種類のプローブ

ZDX が使うプローブは、**Web プローブ**と **Cloud Path プローブ**の2種類です（公式ドキュメント「About Probes」）。

### Web プローブ：アプリの応答を測る

Web プローブは、指定した URL からページを取得し、次の値を測ります。キャッシュは使わず、毎回サーバーから取得します。

| 指標 | 内容 |
|---|---|
| Page Fetch Time | Web ページの取得にかかった時間。最上位の HTML 文書だけを取得し、埋め込まれたリンク先までは取得しない |
| DNS Time | URL のホスト名の名前解決にかかった時間 |
| Server Response Time | 最初の1バイトが届くまでの時間（TTFB） |
| Availability | HTTP の応答コードに基づく可用性。成功なら 1、失敗やタイムアウトなら 0 |

### Cloud Path プローブ：経路を測る

Cloud Path プローブは、端末から宛先までの経路を、途中の**ホップ**（通信が経由する機器）ごとに見える化します。

- 直接インターネットに出る経路（Client Connector → 出口 → 宛先）も、ZIA の Public Service Edge を経由する経路（Client Connector → 出口 → Public Service Edge → 宛先）も表示できる
- 測定する値は、ホップ数、各ホップでのパケットロス率、往復の遅延（平均・最小・最大・標準偏差）
- 応答のないホップは「不明」として点線の矢印で表示される

Web プローブで「遅い」とわかったとき、Cloud Path プローブを見れば、遅延が自宅の Wi-Fi で起きているのか、ISP なのか、その先なのかを絞り込めます。

## 3種類のスコア

設定によって、ZDX スコアには次の3種類があります。

| スコアの種類 | 測り方 |
|---|---|
| Synthetic Probe Score | Web プローブと Cloud Path プローブによる合成監視 |
| RUM Score | 実際の利用者のブラウザでの計測（Real User Monitoring）。ページビュー、ページの読み込み時間、Core Web Vitals などを使う |
| Combined Score | 上の2つを組み合わせたもの |

合成監視は「決まった条件で定期的に測る」ので、比較や傾向の把握に向いています。RUM は「実際に利用者が見た画面」を測るので、体感に近い値が得られます。測り方が違うため、それぞれのスコアは一致しないことがあります。

## アプリの設定：何を監視するか

ZDX で監視するアプリは、次のように設定します（公式ドキュメント「About Applications」）。

- **定義済みアプリ**：Zscaler が用意した主要な SaaS。Web プローブと Cloud Path プローブがあらかじめ設定されており、追加すると自動で有効になる。テナント ID が必要なアプリは、自社のテナント向けの経路を設定することが推奨されている
- **カスタムアプリ**：自社で追加する SaaS や Web アプリ。有効にするには Web プローブを作成する必要がある
- **ネットワークアプリ**：Cloud Path プローブ1つだけで、経路を監視するアプリ
- **ユニファイドコミュニケーション**：Microsoft Teams、Webex、Zoom は、テナントを登録すると通話品質も監視できる。Teams では、通話の信号を扱う URL に加え、音声・映像を中継するサービスへの経路も監視される

## 設計時の判断ポイントと落とし穴

- **何を監視するかを先に決める**：業務で重要なアプリ（メール、Web 会議、基幹 SaaS など）から順に設定します。すべてを一度に監視しようとすると、スコアの意味がぼやけます
- **スコアだけで判断しない**：組織全体のスコアが良くても、特定の拠点や部署だけが悪いことがあります。拠点別・アプリ別に分けて見る習慣をつけます
- **SSL インスペクションの例外を理解する**：公式ドキュメントによると、組織の SSL ポリシーは ZDX の Web プローブには適用されません（それ以外のポリシーは適用されます）。そのため、プローブの結果と、インスペクションを受けた実際の通信の体感は、完全には一致しないことがあります
- **ヘルプデスクの手順に組み込む**：「遅い」という問い合わせを受けたら、まず ZDX でその利用者のスコアと経路を確認する、という流れを決めておくと、切り分けの時間を大きく減らせます

## まとめ

- ZDX は、Client Connector から送るプローブで、端末からアプリまでの体感品質を 0〜100 のスコアにする
- スコアは5分ごとに測定し、1時間の最低値を採るため、一時的な悪化も見逃しにくい
- Web プローブで「アプリの応答」、Cloud Path プローブで「経路のどこが悪いか」を見て、原因を切り分ける

次回は、ZIA・ZPA・ZDX のすべての入口になる Zscaler Client Connector の仕組みを取り上げる予定です。設定の具体的な手順や最新の仕様は、必ず [Zscaler Help](https://help.zscaler.com/zdx) の公式ドキュメントで確認してください。
