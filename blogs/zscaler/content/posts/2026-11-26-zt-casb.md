社内のファイルは共有ドライブではなく SaaS のストレージに、会話はメールではなくチャットに。業務の多くがクラウドアプリの中で行われるようになると、「**誰が、どのクラウドアプリで、何をしているか**」を把握し、危ない使い方を止める仕組みが必要になります。それが **CASB** です。
CASB には大きく、**インライン型**と **API 型（アウトオブバンド）**の2つの方式があります。今回は、Zscaler の公式ガイドをもとに、その違いと使い分けを整理します。

## CASB とは

Zscaler の「SaaS Security Deployment and Operations Guide」は、CASB を次のように説明しています。

- **CASB（Cloud Access Security Broker）**は、クラウドアプリの利用者とクラウドサービスの**間に立つ、可視化と制御のポイント**
- 通信と利用者の操作を監視し、脅威や危険な共有を自動でブロックし、認証やアラートなどのセキュリティポリシーを適用する

ガイドが挙げる CASB の主な効果は次のとおりです。

| 効果 | 内容 |
|---|---|
| データの保護 | 機密データの持ち出しや、危険な共有を防ぐ（DLP） |
| 脅威の防御 | マルウェアなどの脅威を見つけて止める |
| シャドー IT の発見と制御 | 会社が把握していないクラウドアプリの利用を見つける |
| 規制への対応 | 業界の規制や社内の基準に沿った使い方を保つ |

### インライン型（プロキシ型）

**インライン型**は、利用者と SaaS の間の**通信の途中**で中身を見て、その場で制御します。ガイドによると、ZIA では次の機能がインライン型の CASB を担います。

- **クラウドアプリ制御（Cloud App Control）**：アプリごと、操作ごとの制御（11月25日の記事で紹介）
- **脅威対策**と**サンドボックス**：マルウェアなどの検査
- **DLP**：機密データの持ち出しの検知と防止
- **URL フィルタリング**：カテゴリによる制御

管理画面の **Data Security > Inline CASB** には、クラウドアプリ制御のポリシーや、会社が把握していないアプリの利用を見える化する **Shadow IT** のレポートがあります。

### API 型（アウトオブバンド）

**API 型**は、通信の経路の**外（アウトオブバンド）**から、SaaS が用意している **API** を使って、SaaS の中に**保存されているデータ**を調べます。ガイドによると、Zscaler の **SaaS Security API** がこれにあたり、

- データの漏えいを防ぎ、SaaS アプリがルールに沿って使われているかを確かめる
- データの保管場所をスキャンし、クラウドアプリの過去のデータも保持する
- **保存されたデータ（データ・アット・レスト）**を守る

といった役割を持ちます。対象のアプリの種類として、公式ドキュメントにはコラボレーション、ファイル共有、パブリッククラウドのストレージ、ソースコードのリポジトリ、メール、CRM、ITSM、生成AI が挙げられています。

## 何が違うのか

| | インライン型 | API 型（アウトオブバンド） |
|---|---|---|
| 見る場所 | 通信の途中 | SaaS の中（API 経由） |
| 対象のデータ | 動いているデータ（アップロード・ダウンロードの瞬間） | 保存されたデータ（データ・アット・レスト） |
| 止めるタイミング | リアルタイム | 保存されたあと（共有リンクの削除、隔離など） |
| 管理外の端末 | 通信が ZIA を通らなければ見えない | SaaS に保存されれば、どこからのアップロードでも対象 |
| 過去のデータ | 導入前のデータは対象外 | 導入前から保存されているデータも調べられる |
| 前提 | 通信を ZIA に送り、SSL/TLS インスペクションを行う | SaaS のテナントを登録し、API の権限を与える |

一言でいえば、インライン型は「**入口で止める**」、API 型は「**中を点検する**」方式です。どちらか一方では足りないため、両方を組み合わせるのが基本になります（個人の整理です）。
たとえば、私物のスマホから共有ストレージに機密ファイルが置かれた場合、その通信が ZIA を通っていなければインライン型では見えません。API 型なら、保存されたファイルを後から見つけて、共有リンクを外すといった対応ができます。

## API 型の導入の流れ

ガイドに書かれている、API 型（アウトオブバンド）の導入の流れは次のとおりです。

1. 監視したい SaaS アプリを決める
2. **SaaS アプリケーションのテナント**を登録する
3. （任意）保存データの機密情報を見つける **DLP のポリシー**を設定する（先に DLP の設定が必要）
4. （任意）保存データの脅威を見つける**マルウェア検出のポリシー**を設定する
5. **スキャンのスケジュール**を設定する
6. （任意）アクティビティのアラートを調整する

ガイドは、DLP やマルウェア検出のルールで「**報告だけにするか、すぐに対応するか**（共有リンクの削除、マルウェアの隔離など）」を決めるよう勧めています。また、SaaS Security には**追加のライセンス**が必要な場合があります。

11月21日の記事で取り上げた、SSPM のポスチャ結果が AppTotal に表示されなかった障害も、こうした SaaS との**連携（API）**に関わるものでした。API 型は SaaS 側との連携に依存するため、連携の状態を定期的に確認することも大切です。

## よくある落とし穴

- **インライン型だけで安心する**：管理外の端末や、ZIA を通らない経路からのアップロードは見えない
- **API 型を「報告だけ」で放置する**：アラートを見る担当と対応の手順を決めないと、見つけても直らない
- **SSL/TLS インスペクションを除外しすぎる**：インライン型は通信の中身が見えて初めて効く（11月19日の記事参照）

## まとめ

- CASB は、クラウドアプリの利用者とクラウドサービスの間で、利用状況を見える化し、制御する仕組み
- インライン型は通信の途中でリアルタイムに止め、API 型は SaaS の API で保存済みのデータを調べる。Zscaler では、ZIA のクラウドアプリ制御・DLP など（インライン型）と、SaaS Security API（API 型）がこれにあたる
- 両方を組み合わせ、API 型は SaaS のテナント登録、DLP・マルウェア検出のポリシー、スキャンのスケジュールの順に導入する

設定の具体的な手順や最新の仕様は、必ず [Zscaler Help](https://help.zscaler.com/zia) の公式ドキュメントで確認してください。
