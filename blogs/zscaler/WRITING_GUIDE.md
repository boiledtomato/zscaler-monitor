# 執筆ガイド：ゼロトラスト実践ノート（Zscaler ブログ）

`blogs/WRITING_RULES_COMMON.md` の共通ルールに加えて以下に従う。

- 読者：Zscaler を業務で触る初〜中級のネットワーク/セキュリティ担当者
- 出典：help.zscaler.com / trust.zscaler.com / zscaler.com の該当URL、必要に応じて NIST 等の公的文書
- 画像：Zscaler のロゴ・公式画像は使わない（image は付けない）
- 日時は日本時間（JST）を主にし、原文が UTC なら併記する
- help.zscaler.com は JavaScript で描画されるため WebFetch では読めないことが多い。
  関連ドキュメントを確認するときは `node scripts/release_notes_extract.js` と同じ要領で Playwright を使う

## 図（zscaler-update / zscaler-trust-* では必須、zscaler-topic でも推奨）

文章だけでは伝わりにくい「仕組み」「対象範囲」「時系列」を、1記事に2〜3枚の図で示す。
画像ファイルは使わず、本文に SVG を直接書く（ダークモードでも色が切り替わるよう、色は必ず下のクラスで指定する）。

```html
<figure class="fig">
<svg viewBox="0 0 720 200" role="img" aria-label="図の内容を説明する一文">
  ...
</svg>
<figcaption>図1：何を示す図か（出典をもとに作成）</figcaption>
</figure>
```

- 書き方：`<figure>` の前後は空行にし、中には空行を入れない。横幅は viewBox 720 で設計する（スマホでは横スクロールになる）
- 図形：`n`（通常の枠）`na`（強調の枠）`nf`（塗りつぶし・強調）`nm`（薄い塗り）`nx`（警告・問題点の枠）
- 線：`ln`（通常）`la`（強調）`lx`（警告・破線）。矢印は `<marker>` で定義する（id は図ごとに変える）
- 文字：通常は class なし（14px）、`tb`（太字）`tm`（補足・小さめ）`tw`（`nf` の上に置く白抜き文字）
- `fill` や `stroke` を属性で直接書かない（クラスの色が優先され、ダークモードで崩れる）
- 図の例：リリース一覧（OS×日付）、変更前後の比較、通信経路・証明書チェーン、障害の時系列、影響範囲（どのクラウド・DC・設定か）
- 図の中身も本文と同じく、公式情報で確認できた事実だけにする
- 公開前に `python3 scripts/build_site.py` でビルドし、可能ならヘッドレスブラウザで図の表示を確認する

## 週間スケジュール

| 曜日 | 記事 |
|---|---|
| 金・土・月・火 | 製品別アップデート（zscaler-update）。金曜時点でまとめた1週間分を ZCC → ZIA → ZPA → ZDX の順に1日1製品。更新のない製品は飛ばすので、早く終わる週もある |
| 水・木 | 基礎・設計（zscaler-topic） |
| 毎日（不定期） | Trust 記事（zscaler-trust-incident / zscaler-trust-vuln）。新しい対象があるときだけ、1日2本まで |

## zscaler-update（金・土・月・火：製品別アップデート）

- ナビ用タグ：`週次まとめ`（ほかに製品名タグ `ZCC` / `ZIA` / `ZPA` / `ZDX` を必ず付ける）
- タイトル例：「ZIA 週次アップデート（10/30〜11/5）：Advanced SSPM が Kintone に対応ほか」
  — 製品名と対象期間を先頭に、目玉の変更を1〜2個入れる
- ブリーフの全項目に目を通し、**運用者に関係の深いものから**並べる。全部を同じ重さで書かない
- 構成：
  1. 導入：対象期間と、今週いちばん重要な変更を2〜3文で
  2. **今週の一覧表**：項目名（日本語）｜区分（一般提供 / 限定提供 / 修正）｜対象となる人・設定｜重要度（高・中・低）
  3. 主な変更ごとに `##` 見出しで、次の4点を必ず書く
     - **何が変わったか**：原文を要約（丸写ししない）
     - **どんな機能か**：その機能をまだ知らない読者向けに、前提となる機能を1〜3文で説明
     - **対象となる人・設定**：どの設定を入れている人が影響を受けるか具体的に
       （例：「Transparent Proxy-based Interception モードの macOS 端末」「App Store Group Policy で段階配信を使っている管理者」
       「Advanced SSPM のライセンスがあるテナント」）。原文に条件がなければ「全テナント」とせず「原文に記載なし」と書く
     - **運用者がやること**：確認・設定変更・告知など。何もしなくてよい場合はそう書く
  4. 細かい修正（Fixes）は表か箇条書きでまとめる
  5. まとめ：3行
- ZCC は OS とバージョンを表にする（OS｜バージョン｜区分｜主な内容）。「Limited Availability（限定提供）」は
  全員に配られるわけではないことを明記する
- 原文の機能名・設定名は英語のまま併記する（管理画面で探せるように）。例：「段階配信（Phased Rollout）」
- 分量：本文 3,000〜6,000 文字（項目数に応じて）。シリーズの次回（翌営業日の製品）に一言触れる
- 項目の詳細が足りないときは「関連ドキュメント」の URL を読んで補う。確認できない細部は書かないか「公式情報で要確認」

## zscaler-trust-incident（不定期：障害の振り返り）

- ナビ用タグ：`障害・脆弱性`（ほかに影響製品タグ `ZIA` / `ZPA` / `ZCC` など、`障害` タグを付ける）
- 対象：trust.zscaler.com の「Recent incident」のうち、解決済み（Resolved）で原因（Root Cause）が公表されたもの
- タイトル例：「【障害】zscaler.net でデバイス登録が断続的に失敗（11/10）：原因と影響」
- 構成：
  1. 導入：何が起きたかを2〜3文で
  2. **概要表**：発生・解決日時（JST と UTC）｜対象クラウド・データセンター｜種別（Service Degradation など）｜影響｜検知経路
  3. **何が起きたか**：利用者から見た症状
  4. **原因**：公式の Root Cause を日本語で正確に説明する。原文にない推測を書く場合は「推測」と明記して分ける。
     専門用語（トランジットプロバイダー、フェイルオーバーなど）には一言説明を添える
  5. **影響を受けた人・設定**：どのクラウド・DC・機能・設定の利用者が影響を受けたか
  6. **時系列**：原文の Update を時刻順に表で
  7. **運用者が学べること**：同様の障害時の切り分け手順、副系DCへの切り替え、監視（ZDX など）の活用
  8. まとめ：3行
- 分量：本文 2,000〜4,000 文字。障害を煽らず、事実ベースで書く

## zscaler-trust-vuln（不定期：脆弱性への対応）

- ナビ用タグ：`障害・脆弱性`（ほかに `脆弱性` タグと CVE 番号のタグを付ける）
- 対象：trust.zscaler.com の CVE に関するアドバイザリ
- タイトル例：「【脆弱性】CVE-2026-98432（Linux カーネル）への Zscaler の対応と、利用者がやること」
- 構成：
  1. 導入：どんな脆弱性で、Zscaler 利用者に関係があるかを2〜3文で
  2. **概要表**：CVE 番号｜対象ソフトウェア｜Zscaler の見解（影響あり／なし／調査中）｜利用者の対応要否｜公開日
  3. **どんな脆弱性か（原因）**：脆弱性の仕組みを、原文と広く確立した知識の範囲で説明する。
     CVSS スコアや攻撃手法の詳細は、原文や NVD 等で確認できたものだけ書く
  4. **Zscaler のクラウドへの影響**：原文の見解をそのまま正確に
  5. **利用者が管理するコンポーネントへの影響**：App Connector、Private Service Edge、Branch/Cloud Connector など、
     利用者が OS を管理するものについて、原文の推奨を具体的な作業に落とす
  6. まとめ：3行
- 分量：本文 2,000〜4,000 文字。原文が「調査中」のときはそう明記し、断定しない

## zscaler-topic（水・木：基礎・設計解説）

- ナビ用タグ：`基礎`
- 仕組み → 設計時の判断ポイント → よくある落とし穴 の流れで書く。
- 仕様の細部は公式ドキュメントで確認できたものだけを書く。

## zscaler-digest（旧形式・現在は使わない）

2026-11-09 までの月曜週次まとめ。過去記事のタグ `週次まとめ` はそのまま残す。
