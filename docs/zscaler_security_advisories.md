Type: security
Status: In Progress

Body: Zscaler is aware of reports of&nbsp; compromised TLS intermediate certificates associated with digital certificate provider eMudhra .&nbsp; Zscaler found no evidence of compromise within the Zscaler environment. The Zscaler Engineering and Security teams conducted an exhaustive investigation to identify and remove all relevant certificates from our products’ root certificate bundles. Zscaler does not rely internally on eMudhra certificates or services but has taken the following actions and provides the following recommended guidance for customers. Internet &amp; SaaS (ZIA) Cloud Platform The Internet &amp; SaaS cloud platform has been updated to remove impacted intermediate certificates from the root certificate bundle associated with eMudhra. Private Access (ZPA) Cloud Platform Zscaler has identified no impact to the Private Access cloud platform at this time. Out of an abundance of caution, Zscaler removed the impacted intermediate certificates from the root certificate bundle associated with eMudhra. Root certificate bundle updates will be applied to Private Access cloud platforms during each region’s scheduled maintenance window in accordance with our standard change-management procedures.&nbsp; No service disruption is anticipated as a result of this activity . Private Access-Distributed Software Products Zscaler has released a software update (version number 26.58.5) to remove impacted intermediate certificates from the root certificate bundle associated with eMudhra in the following customer-deployed products: App Connectors Private Service Edges Private Cloud Controllers Network Connectors Zscaler recommends updating these components at the earliest opportunity to protect against Man-in-the-Middle attacks leveraging the compromised intermediate certificates.&nbsp; Zscaler automatically deploys the updates during your regularly scheduled upgrade windows as outlined in&nbsp; Scheduling Periodic Software Updates in Private Access . If you are concerned and would like to manually update Private Access components immediately, follow the steps in&nbsp; Configuring a Version Profile with the&nbsp; New Release 26.58.5 , and schedule the update. Additionally, if your organization has TLS certificates issued by eMudhra intermediate CAs, those certificates will no longer be trusted by Private Access after this update. Contact your certificate provider or Zscaler Support if you believe this applies to you. Zscaler recommends that customers&nbsp; upgrade any customer maintained operating systems according to vendor recommendations for the most secure environment. Zero Trust Browser The Zero Trust Browser platform has been updated to address exposure associated with the compromised intermediate certificates.&nbsp; Additional Security Guidance Customers are advised to apply all relevant vendor, operating system, and platform certificate updates promptly, especially in environments that use independently managed trust stores or custom certificate bundles. Zscaler will continue to monitor the situation closely and provide necessary updates. Update&nbsp; Mon, 26 Oct 2026 14:25:12 UTC &nbsp; While Zscaler has removed impacted certificates from its Root Certificate Bundle, Zscaler recommends customers to audit their SSL/TLS inspection policies specifically for handling untrusted certificates:&nbsp; Review all applicable&nbsp; SSL/TLS inspection policies and set Untrusted Server Certificates to&nbsp; Block . If there is a business need to allow untrusted certificates for specific domains: Create a separate SSL/TLS inspection policy isolated to those domains to&nbsp; Allow untrusted certificates. Configure all other existing SSL/TLS inspection policies to Block untrusted certificates, including the Zscaler Default SSL_TLS Inspection Rule. Any SSL/TLS policy that does not explicitly block untrusted certificates leaves your traffic exposed to potential Man In The Middle (MITM) attacks. Update 2&nbsp; Sat, 07 Nov 2026 01:25:10 UTC &nbsp; Zscaler Client Connector (ZCC) Zscaler has released Zscaler Client Connector (ZCC) software updates that remove impacted intermediate certificates associated with eMudhra from the Zscaler root certificate bundle. Android:&nbsp; 5.0.0.344 ChromeOS: 5.0.0.344 Linux: versions 3.7.2.80, 4.2.0.66, 4.2.1.126,&nbsp;4.2.2.154 Customers should update to the applicable release at the earliest opportunity to help protect against potential man-in-the-middle attacks that could leverage compromised eMudhra intermediate certificates. To maintain continuous secure connectivity and ensure uninterrupted technical support, all organizations operating Cloud Connector (CC) and Branch Connector (BC) infrastructure on ZSOS24 must execute their respective transition paths prior to the EOL date. The migration pathways are determined by appliance form factor: Virtual Connectors (Cloud Connector &amp; Virtual Branch Connector): Mandatory Redeployment to ZSOS42: Due to major architectural enhancements, new kernel baselines, and modified disk partitioning structures, in-place automated OS upgrades are not supported. All virtual instances in AWS, Azure, GCP, VMware ESXi, Linux KVM, and Microsoft Hyper-V must be redeployed using official&nbsp; ZscalerOS 42 (ZSOS42) images. &nbsp; Physical Branch Connector Appliances: Gateway mode: Most physical Branch Connector appliances deployed in gateway mode have already been upgraded to ZscalerOS 42 (ZSOS42) automatically. The exception is tenants for which an upgrade block was requested through Zscaler Support. If an upgrade block is in place on your tenant, contact Zscaler Support to have it removed so the appliances can be upgraded before December 31, 2026. To check which version your appliance is currently running, see&nbsp; How to validate if a Zscaler VM is running ZSOS24 and needs redeployment . One-Armed mode: Physical Branch Connector appliances deployed in One-Armed mode are not upgraded automatically. These appliances must be upgraded to ZSOS42 manually by redeploying them before December 31, 2026. For the procedure, see&nbsp; Redeploying hardware Branch Connector in One-Armed mode (non-gateway mode) . Zscaler strongly recommends auditing active connector deployments immediately, updating deployment automation templates, and initiating branch hardware migration planning well in advance of December 31, 2026. Why Deployments Running ZSOS24 Are In Scope Operating System Lifecycle Retirement: ZSOS24 has reached the conclusion of its development and security maintenance cycle. Subsequent security vulnerabilities, compliance hardening, cryptographic updates, and feature enhancements are developed exclusively on ZSOS42 and modern platform baselines. Architecture and Partitioning Changes (Virtual): The shift from ZSOS24 to ZSOS42 introduces an updated disk partitioning scheme and underlying filesystem modifications that cannot be applied dynamically to existing virtual disks, requiring clean instance provisioning. Support Policy: After December 31, 2026, Zscaler Support and Engineering will no longer provide hotfixes, maintenance patches, or issue investigations for systems running ZSOS24.&nbsp; Potential Impact If No Action Is Taken Virtual Cloud and Branch Connector Appliances (ZSOS24) Security &amp; Compliance Deficits: Virtual instances remaining on ZSOS24 after December 31, 2026, will not receive OS-level vulnerability fixes, leaving workloads exposed and potentially out of compliance with regulatory standards. Control-Plane and Feature Incompatibility: As the Zscaler Zero Trust Exchange continues to modernize communication protocols and forwarding services, legacy ZSOS24 nodes risk operational degradation or loss of synchronization. Support Remediation Requirements: For support cases opened after the EOL date, customer support will require immediate redeployment to a supported ZSOS42 release as a prerequisite for assistance. Deployment Automation &amp; CI/CD Pipelines Unmodified Terraform definitions, CloudFormation stacks, and ARM/Bicep templates referencing ZSOS24 image identifiers will spin up unsupported, non-compliant virtual instances. Required Action: Migration and Redeployment Procedures Administrators must inventory all running appliances across public cloud environments, local hypervisors, and physical branch sites, executing the appropriate procedure for each form factor. Determine Active ZSOS Software Versions Administrators can determine the installed ZscalerOS version by accessing the Cloud Service Provider console or via SSH to the instance. Detailed validation instructions are available on the Zscaler Community: Guide for&nbsp; Cloud Connectors Guide for&nbsp; Branch Connectors Redeployment Procedure for Virtual Appliances (Cloud &amp; Branch Connectors) Virtual Cloud Connectors and Branch Connectors running ZSOS24&nbsp; must be redeployed using official ZSOS42 images, as in-place OS upgrades are not supported. For step-by-step validation and migration instructions, refer to the&nbsp; Zscaler Community Migration Guide . Update Infrastructure as Code (IaC) Templates Update all Terraform modules (terraform-azurerm-cloud-connector-modules, AWS/GCP modules), CloudFormation scripts, and ARM/Bicep templates to reference active ZSOS42 image URNs or AMIs. Update auto-scaling configurations and launch templates for Virtual Machine Scale Sets (VMSS) and Auto Scaling Groups (ASG) to prevent new deployments of legacy images. Migration Procedure for Physical Branch Appliances (Transition to Zero Trust Branch) Physical Branch Connector hardware appliances cannot be upgraded to ZSOS42. Organizations must transition physical sites to&nbsp; Zero Trust Branch : Transition Path to Zero Trust Branch (ZTB): Deploy native&nbsp; Zero Trust Branch hardware appliances to replace physical Branch Connectors at designated branch offices and campus environments. Zero Trust Branch appliances natively connect users, servers, and IoT/OT devices to the Zero Trust Exchange without requiring local routable overlays or legacy hub-and-spoke topologies. &nbsp; Modernization Advantages: &nbsp; Eliminates complex branch site-to-site VPN tunnels and traditional SD-WAN hardware sprawl. Simplifies ongoing lifecycle management through centralized, cloud-native administration. &nbsp; Action Required: &nbsp; Engage your Zscaler Account Team or Solutions Architect to assess site requirements and coordinate the acquisition, sizing, and deployment schedule for Zero Trust Branch hardware before the December 31, 2026 deadline. Key Dates and Deadlines Date Milestone / Event September 2026 Formal EOL Customer Advisory published. Fleet inventory audit begins; Zero Trust Branch hardware planning commences. October 1 – November 30, 2026 Recommended window to complete virtual appliance blue-green redeployments to ZSOS42 and roll out Zero Trust Branch hardware across physical sites. Caveats and Considerations Hardware Procurement Lead Times: Because physical branch connectors must be replaced with Zero Trust Branch appliances, account for hardware supply chain, shipping, and on-site cutover timelines well prior to the December 31, 2026 deadline. When is the update scheduled? These Debian packages have already been removed and are no longer available for download.&nbsp; What are my next steps? Discontinue installing any of the affected Debian packages noted above.&nbsp; Look forward to new Debian packages for refresh builds of these affected versions being made available over the next week.&nbsp; When those are available, you will need to install them manually. Title: Required Action: Opt Out of Microsoft Azure Network Adapter (MANA) for Zscaler Cloud Connectors Deployed in Microsoft Azure
Type: other_advisory
Status: In Progress
Posted: Sat, 18 Jul 2026
Created: 2026-07-18 22:50:59
Body: Microsoft is currently deploying the&nbsp; Microsoft Azure Network Adapter (MANA) , a next-generation network interface included within Azure Boost, across existing Azure virtual machine (VM) size families. This deployment will replace the Mellanox ConnectX-based Accelerated Networking hardware currently utilized by Cloud Connector. Effective&nbsp; August 1, 2026 , Azure may automatically transition MANA-eligible VMs to MANA-capable hardware during routine lifecycle events, unless an explicit opt-out is configured. Zscaler formally recommends that all customers implement Microsoft's MANA opt-out configuration (via the&nbsp; LegacyVMNVA tag) across all Azure resource groups, virtual machines (VMs), and VM Scale Sets hosting Cloud Connectors prior to August 1, 2026. Pending Zscaler's official announcement regarding Microsoft Azure Network Adapter (MANA) driver support for Cloud Connector, it is imperative that all Cloud Connector instances continue to utilize Mellanox-based Accelerated Networking. This configuration remains the established, validated methodology for Cloud Connector deployments. Zscaler is currently engaged in the active development of comprehensive MANA driver support. Why Cloud Connector Is In Scope Accelerated Networking is enabled by default across all Cloud Connector deployments within the Azure Marketplace. Microsoft's opt-out directives specifically target this category of workloads, namely Network Virtual Appliances (NVAs) utilizing Accelerated Networking. The supported instance sizes for Cloud Connector are included in Microsoft's MANA-eligible classification. The standard Cloud Connector dimensions recommended by Zscaler, specifically&nbsp; Standard_D2s_v3 and&nbsp;Standard_DS2_v2, Standard_DS3_v2, Standard_D2ds_v4, and Standard_D2ds_v5&nbsp; fall within the specific versions encompassed by the MANA deployment. Network Virtual Appliance (NVA) workloads experience a distinct impact due to their immediate reliance on the underlying network hardware and drivers, in accordance with the guidance provided by Microsoft. Potential Impact If No Action Is Taken Currently Active Cloud Connectors (Deployed prior to August 1, 2026): These instances are currently deployed on non-MANA hardware. Subsequent to August 1, 2026, any lifecycle event affecting the Cloud Connector (such as stop/start, redeploy, or reapply) may result in the virtual machine (VM) being allocated to MANA-enabled hardware. In the event that the VM is placed on MANA-enabled hardware, Zscaler applications will fail to initialize on that instance. Currently Active Virtual Machine Scale Sets (VMSS): Cloud Connector instances within a VMSS are currently deployed on non-MANA hardware. Following August 1, 2026, any lifecycle event at the VMSS level (Scale-Out, Scale-In) or at the individual Cloud Connector level (stop/start, redeploy, or reapply) may cause the VM to be provisioned on MANA-enabled hardware. If any VM within a VMSS is allocated to MANA-enabled hardware, Zscaler applications will fail to initialize on that specific VM. Newly Deployed Cloud Connectors (With or Without Scale Sets): If a new deployment of Cloud Connector VMs is allocated to MANA-enabled hardware, Zscaler applications will fail to initialize on those instances. Required Action before Aug 1 2026: Apply the Microsoft Opt-Out It is recommended to apply Microsoft's&nbsp;LegacyVMNVA opt-out configuration by adhering to the official guidance:&nbsp; MANA support for Network Virtual Appliances (NVAs) . 1. At scale (recommended) It is recommended to assign Microsoft's built-in&nbsp; LegacyVMNVA Azure Policy , incorporating&nbsp; compliance remediation , across all subscriptions or resource groups that contain Cloud Connectors. This policy applies the tag to both individual virtual machines and Virtual Machine Scale Sets. Microsoft advises assigning the built-in policy as-is to ensure that subsequent updates are automatically propagated.. 2. Individual VMs Apply the&nbsp;LegacyVMNVA tag, requiring no associated value, to each individual Cloud Connector Virtual Machine (VM). Provided that the Cloud Connector VM is currently executing on non-MANA-enabled hardware, the presence of this tag guarantees that the instance will persist on non-MANA-enabled infrastructure during any subsequent lifecycle events. 3. VM Scale Sets Apply the&nbsp;LegacyVMNVA tag to the scale set model. For existing instances, update the tag separately utilizing the following command: az vm update --resource-group &lt;rg-name&gt; --name &lt;instance-name&gt; --set tags.LegacyVMNVA='"true"' Alternatively, a rolling instance replacement subsequent to tagging the model achieves an identical outcome. It is necessary to verify that instances generated by scale-out events after tagging inherit the tag. 4. Infrastructure as Code If you deploy Cloud Connectors via the Zscaler Terraform modules (zscaler/cloud-connector-modules/azurerm) or your own templates,&nbsp; add the&nbsp;LegacyVMNVA tag to your VM and VMSS resource definitions so that all future deployments and scale-out instances carry the tag from creation. VMs created after August 1, 2026 without the tag may be placed directly on MANA-capable hardware. Verification Confirm the&nbsp;LegacyVMNVA tag is visible on each Cloud Connector VM and VMSS in the Azure portal. Azure Advisor raises recommendations against affected NVAs; use it to identify untagged Cloud Connectors. If you suspect an instance has already been placed on MANA hardware (indicated by a MANA Virtual Function visible to the guest), contact Zscaler Support for verification, apply the tag, and perform a stop/deallocate/start to return the instance to Mellanox-based hardware. Recovery Steps if Impacted: In the event that a Cloud Connector virtual machine (VM) is allocated to MANA-capable hardware, please execute the following remediation procedures to restore the instance. Note that these recovery operations are exclusively applicable to a VM subsequent to its allocation to MANA-capable hardware. If the configurations specified in the “Required Action: Apply the Microsoft Opt-Out” section have been properly implemented, Cloud Connector VMs will be completely precluded from getting placed on MANA-enabled hardware entirely. Apply the opt out tag &nbsp; &nbsp; &nbsp;az vm update -g &lt;resource group name&gt; -n &lt;vm instance name&gt; --set tags.LegacyVMNVA="" Deallocate &nbsp; &nbsp; &nbsp;az vm deallocate -g &lt;resource group name&gt; -n &lt;vm instance name&gt; Start &nbsp; &nbsp; &nbsp;az vm start -g &lt;resource group name&gt; -n &lt;vm instance name&gt; How to check if Cloud Connector VM is placed in MANA enabled hardware In the event that a Cloud Connector virtual machine (VM) is allocated to MANA-enabled hardware, an unattached PCI device appears within the PCI configuration when the following command is executed:&nbsp; pciconf -lv | grep -iEA 3 'class=0x020000.*vendor=0x1414.*device=0x00ba' none1@pci1:0:0:0: &nbsp; &nbsp; &nbsp; &nbsp; class=0x020000 rev=0x00 hdr=0x00 vendor=0x1414 device=0x00ba subvendor=0x1414 subdevice=0x00b9 &nbsp;&nbsp;&nbsp;&nbsp;vendor &nbsp; &nbsp; = 'Microsoft Corporation' &nbsp;&nbsp;&nbsp;&nbsp;class&nbsp; &nbsp; &nbsp; = network &nbsp;&nbsp;&nbsp;&nbsp;subclass &nbsp; = ethernet Key Dates (Azure Public Cloud) Date Event May 26, 2026 Azure began placing Intel v5 and Cobalt 100 v6 family VMs on MANA-capable hardware in select regions. May 31, 2027 The&nbsp;LegacyVMNVA opt-out sunsets. From June 1, 2027, all MANA-eligible VMs may be placed on MANA-capable hardware regardless of tagging. Caveats and Additional Notes On-Demand Capacity Reservations (ODCR): Applying&nbsp;LegacyVMNVA to VMs under an ODCR reduces the available capacity pool for placement, and ODCR SLA guarantees do not apply to those VMs while tagged. The opt-out mechanism is proprietary to and maintained exclusively by Microsoft. For technical errors encountered during the enforcement of the Azure Policy or the configuration of the tag, please contact Microsoft Azure support. For inquiries pertaining to Cloud Connector operational behavior or performance characteristics, please contact Zscaler Support. The opt-out mechanism is temporary and does not constitute a permanent exemption. It is recommended to utilize the period prior to May 31, 2027, to plan the migration to MANA-validated Cloud Connector software (referenced below).. Long-Term Resolution Zscaler is currently collaborating with Microsoft to validate the MANA driver stack for Cloud Connector. Announcements regarding MANA support will be disseminated via the&nbsp; Cloud Connector release notes . Upon the availability of a MANA-validated Cloud Connector release, customers should plan to upgrade to that specific version or subsequent versions prior to the&nbsp; May 31, 2027 opt-out sunset, after which all MANA-eligible VMs will be transitioned to MANA-capable hardware.
